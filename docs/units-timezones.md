# Units, time zones and preferences

Authenticated `GET /api/v1/account/preferences` returns `{ "weightUnit": "kg", "timeZoneId": "Etc/UTC" }` by default. `PUT` accepts the same two required fields and returns the saved preferences. Weight unit is exactly `kg` or `lb`; time zone is a known IANA identifier, at most 100 characters. Windows identifiers and arbitrary UTC offsets are not accepted. Preferences belong to the authenticated account, and updates are last-write-wins. A phone's zone is only a suggested value until explicitly saved. Existing accounts retain their identity and get these defaults on migration.

There is no weight or workout API yet. Future writes will provide a decimal value and `kg` or `lb` at the API boundary. External weight may be zero but cannot be negative; completed sets require positive integer repetitions. Inputs have at most three fractional digits. One pound is exactly 0.45359237 kg. Convert using decimal arithmetic once, round kilograms to three places using midpoint away from zero, and store as PostgreSQL `numeric(10,3)`, with a maximum of 9,999,999.999 kg. Reject values outside the range before conversion or rounding. Responses use canonical kilograms; display conversion to the preferred unit uses at most three fractional digits with trailing zeros trimmed. Changing the preference must never rewrite a stored canonical value. Decimal text entry must handle Dutch and English separators without accepting ambiguous grouping. Shared examples are in `contracts/fixtures/units-timezones.json`.

External load is either total load or per dumbbell according to the exercise's load convention. Do not compare loads with different conventions as the same exercise. Bodyweight and assisted movements need explicit future models.

Future sessions record UTC instants and the IANA time zone captured for that session separately. Determine a history day by converting the instant to that recorded zone, including its daylight-saving rules; later account preference changes must not change the recorded zone. Time-zone rules depend on installed tzdata and may be revised. PostgreSQL `timestamp with time zone` stores an instant, not the zone identifier. See [Npgsql date/time handling](https://www.npgsql.org/doc/types/datetime.html), [Npgsql numeric mapping](https://www.npgsql.org/doc/types/basic.html), and [.NET time-zone resolution](https://learn.microsoft.com/en-us/dotnet/api/system.timezoneinfo.findsystemtimezonebyid?view=net-10.0).
